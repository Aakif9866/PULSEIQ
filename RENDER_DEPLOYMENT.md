# Deploying PulseIQ on Render (Blueprint)

PulseIQ deploys to [Render](https://render.com) from one file,
[`render.yaml`](render.yaml), a Render **Blueprint**. Render reads it from
GitHub and creates both services with their settings, so nothing is clicked
together by hand.

> **Status:** the Blueprint and the Docker image are verified locally under
> the free tier's limits (512 MB memory, `PORT=10000`). A live Render deploy
> is created from this guide; record the live URLs in the README once it
> passes the checks in step 5.

## What gets deployed

```
Browser ──► pulseiq-aakif.onrender.com        Static site (React build)
              │  HTTPS, CORS
              ▼
           pulseiq-aakif-api.onrender.com    Web service (Docker, FastAPI)
              ├──► Neon Postgres              users, history, dashboards, usage
              ├──► Cloudflare R2 (pulse-iq)   uploaded files, private
              └──► Groq API                   language model
```

| Service | Render type | Plan | Source |
|---|---|---|---|
| `pulseiq-aakif-api` | Web service, runtime `docker` | Free | `backend/Dockerfile` |
| `pulseiq-aakif` | Static site | Free | `frontend/`, `npm ci && npm run build`, publishes `dist` |

Both deploy from branch `feature/pulseiq-v2-roadmap` and redeploy
automatically on every push to it. The database (Neon) and file storage (R2)
live outside Render, so data survives restarts, sleeps, and redeploys.

The names are deliberate: `pulseiq-api` and `pulseiq` on `onrender.com`
belong to someone else's suspended services. With unique names, the URLs
baked into `render.yaml` (`VITE_API_URL`, `CORS_ORIGINS`, the CSP) are the
real ones on the first deploy.

## What `render.yaml` configures

**Backend (`pulseiq-aakif-api`)**

- Builds `backend/Dockerfile`: multi-stage, runs as a non-root user.
- On every start it runs `alembic upgrade head`, then the demo seeder,
  then uvicorn on Render's `$PORT`.
- Health check: `GET /api/v1/health`.
- Environment it sets for you:

| Variable | Value | Why |
|---|---|---|
| `ENVIRONMENT` / `DEBUG` | `production` / `false` | The app refuses to start in production with debug on or the default secret |
| `SECRET_KEY` | generated by Render | Signs login tokens |
| `STORAGE_PROVIDER` / `R2_BUCKET_NAME` | `r2` / `pulse-iq` | Uploads go to R2 |
| `MAX_UPLOAD_SIZE_MB` | `25` | A 50 MB file measured ~611 MB peak memory, over the free 512 MB |
| `MAX_DATASETS_PER_USER` | app default `5` | Per-account limit |
| `AI_PROVIDER` / `GROQ_MODEL` | `groq` / `openai/gpt-oss-120b` | Language model |
| `AI_DAILY_TOKEN_QUOTA_PER_USER` | `30000` | Per-user daily AI budget |
| `AI_DAILY_TOKEN_QUOTA_GLOBAL` | `180000` | Whole-app cap, under Groq free tier's 200k/day |
| `TRUSTED_PROXY_HOPS` | `1` | Rate limiter reads the client IP Render's edge appends |
| `DEMO_USER_EMAIL` | `demo@pulseiq.dev` | Shared demo account |
| `CORS_ORIGINS` | `["https://pulseiq-aakif.onrender.com"]` | Only the frontend may call the API |

**Frontend (`pulseiq-aakif`)**

- `VITE_API_URL=https://pulseiq-aakif-api.onrender.com/api/v1`, baked into
  the build.
- Rewrite `/* → /index.html`, so deep links and refreshes work.
- Response headers: Content-Security-Policy (scripts only from itself, API
  calls only to the backend), HSTS, `X-Frame-Options: DENY`, nosniff,
  `Referrer-Policy`, `Permissions-Policy`, and a one-year cache on hashed
  `/assets/*` files.

## Step by step

### 1. Prerequisites

- The code is pushed to GitHub (`Aakif9866/PULSEIQ`, branch
  `feature/pulseiq-v2-roadmap`).
- A **Neon** Postgres database and its connection string.
- A **Cloudflare R2** bucket named `pulse-iq` and an R2 API token with
  read/write on it. Use the account ID, not the public `pub-….r2.dev`
  URL; the app rejects that URL on purpose.
- A **Groq** API key.

### 2. Create the Blueprint

1. Sign in at [dashboard.render.com](https://dashboard.render.com) with GitHub.
2. **New → Blueprint**, then pick the `Aakif9866/PULSEIQ` repository.
3. Give the Blueprint a name (e.g. `pulseiq`). Render lists the two services
   from `render.yaml`.

You never choose a language or runtime: the Blueprint sets Docker for the
backend and a static site for the frontend. If Render asks for a language,
you're on the **New → Web Service** form instead; go back and pick
**Blueprint**.

### 3. Fill in the six secrets

Render prompts only for the values marked `sync: false` in `render.yaml`:

| Variable | Where it comes from |
|---|---|
| `DATABASE_URL` | Neon → Connection string (`postgresql://…neon.tech/neondb?sslmode=require…`) |
| `GROQ_API_KEY` | Groq console (starts with `gsk_`) |
| `DEMO_USER_PASSWORD` | The demo password published in the README |
| `R2_ACCOUNT_ID` | Cloudflare dashboard, R2 overview |
| `R2_ACCESS_KEY_ID` | R2 API token |
| `R2_SECRET_ACCESS_KEY` | R2 API token |

Paste values exactly, with no quotes or spaces. Leave `R2_ENDPOINT_URL`
unset; it's derived from the account ID.

### 4. Apply

Click **Apply**. The backend's first Docker build takes about 5–10 minutes;
the static site takes 1–2. On first start the backend:

1. migrates the database to the latest revision (currently `0010`);
2. creates the demo user, uploads the sample dataset to R2, and builds the
   demo dashboard;
3. starts serving, and Render marks it **Live** once `/api/v1/health`
   answers.

### 5. Verify

```bash
curl https://pulseiq-aakif-api.onrender.com/api/v1/health
# {"status":"ok","storage_provider":"r2","max_upload_size_mb":25,"max_datasets_per_user":5}
curl -I https://pulseiq-aakif.onrender.com/ | grep -i content-security-policy
```

Then in a browser:

1. Open `https://pulseiq-aakif.onrender.com`, which shows the landing page
   with the sign-up count.
2. Log in as `demo@pulseiq.dev`; the sample dataset and dashboard should be
   there.
3. Ask an AI question, and confirm the browser console shows no CSP errors.
4. Refresh on a deep link (e.g. `/workspace/datasets`); it should load, not 404.

## Day-to-day operation

**Deploying changes.** Push to `feature/pulseiq-v2-roadmap`; both services
redeploy. To deploy from `main` instead, change `branch:` in `render.yaml`.

**Migrations.** They run at container start, before the app serves. That's
safe with one instance (the free plan). Before scaling to several, move
`alembic upgrade head` into a separate release step so two instances never
migrate at once. Every migration so far is additive.

**Rollback.** Render dashboard → service → **Events** → pick an earlier
deploy → **Rollback**. Database migrations are not rolled back
automatically; `alembic downgrade -1` is available if a migration itself
must be undone.

**Free-tier behaviour.** The backend sleeps after 15 minutes without
traffic; the first request afterwards takes about a minute. The static site
never sleeps.

**Logs and monitoring.**
- Logs: Render dashboard → service → **Logs** (structured JSON, every line
  has a `request_id`; users see the same id as "Reference" on errors).
- Errors: set `SENTRY_DSN` on the backend to send errors to Sentry (no
  personal data is sent). Off when unset.
- Uptime: point a free monitor (e.g. UptimeRobot) at `/api/v1/health`. On
  the free plan a 5-minute check also keeps the backend from sleeping, but
  it uses free-tier instance hours.

**Backups.** Neon keeps a restore window for point-in-time recovery; check
your Neon plan for its length. R2 objects aren't versioned by default;
uploaded files can be re-uploaded by their owners, and the demo dataset is
re-seeded on every deploy.

**Rotating secrets.** Change the value under the backend's
**Environment** tab and Render redeploys. Rotating `SECRET_KEY` signs
everyone out, which is expected.

## Changing the domain

If the services get different URLs, or you add a custom domain, update all
of these together:

| Where | What |
|---|---|
| `render.yaml` → backend `CORS_ORIGINS` | The frontend's origin |
| `render.yaml` → frontend `VITE_API_URL` | The backend's `/api/v1` URL |
| `render.yaml` → frontend CSP `connect-src` | The backend's origin |
| `frontend/index.html` | `canonical`, `og:url`, `og:image`, `twitter:image`, JSON-LD `url` |
| `frontend/public/robots.txt`, `sitemap.xml` | Site origin |

Then push. With a single custom domain for both (e.g. `app.example.com` and
`api.example.com`), login tokens could move to first-party httpOnly cookies;
see `docs/SECURITY.md`.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Backend build fails on `pip install` | A pinned package can't install. Check the build log for the package name |
| Backend restarts in a loop | Usually `DATABASE_URL` is wrong or Neon is unreachable; the log shows the Alembic error |
| `storage_provider` is `local` in `/health` | `STORAGE_PROVIDER` didn't apply; check the backend's Environment tab |
| R2 `AccessDenied` / `401` | Wrong token, or an `r2.dev` URL set as the endpoint |
| Frontend loads but every API call fails | `VITE_API_URL` / `CORS_ORIGINS` / CSP `connect-src` don't match the real URLs |
| "Too many requests" for everyone | `TRUSTED_PROXY_HOPS` isn't `1`, so every user shares Render's proxy IP |
| AI answers stop for everyone | The daily `AI_DAILY_TOKEN_QUOTA_GLOBAL` was reached; it resets at midnight UTC |
| Upload returns 413 | The file is over `MAX_UPLOAD_SIZE_MB` (25 on the free plan) |
| Everyone was signed out after a deploy | Expected once for migration `0010`: sessions from before it can't refresh |

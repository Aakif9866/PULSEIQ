# Security

The actual security model implemented, and its known limitations, stated
plainly. **This is not a claim of enterprise security or a completed
audit** — it's an honest account of what exists today.

## Authentication

JWT (HS256), issued as an access token (24h) and refresh token (14d) on
signup/login. Passwords hashed with bcrypt via `passlib`. `SECRET_KEY`
signs every token; `app/core/config.py` has a hard startup guard —
`Settings` **refuses to even construct** if `ENVIRONMENT=production` and
`SECRET_KEY` is still the insecure placeholder, or if `DEBUG=true` in that
environment. Verified live: importing the app with those settings raises
immediately, before anything else runs.

## Protected routes & user resource isolation

Every route that touches a user's data requires a valid bearer token
(`get_current_user`, a FastAPI dependency). Every dataset/insight/
dashboard/dashboard-chart lookup is scoped to `owner_id = current_user.id`
at the repository layer — there is no query anywhere that can return
another user's row.

**Verified directly, not assumed:** attempting to read, query, delete, or
attach a chart to another user's dataset/dashboard/insight returns `404`,
not `403` — deliberately, so a user can't even confirm a resource exists
under someone else's account. Covered by dedicated cross-tenant tests for
every resource type (see `docs/TESTING.md`).

## File upload validation

- **Extension allowlist**: only `.csv`, `.xlsx`, `.xls` accepted
  (`ALLOWED_UPLOAD_EXTENSIONS`); anything else is rejected before the file
  touches storage.
- **Size limit**: `MAX_UPLOAD_SIZE_MB` (default 200), enforced before any
  database or storage write — a rejected upload leaves no trace.
- **Content is validated by actually trying to profile it.** A file with
  the right extension but garbage/corrupted content (verified with random
  bytes named `.xlsx`) fails profiling cleanly (`status=profiling_failed`)
  rather than crashing the request.

## Path traversal prevention

Storage keys are **never** derived from a client-supplied filename — a key
is always `{owner_id}/{a fresh server-generated uuid4}{extension}`; the
original filename is kept only as display metadata in Postgres, never
used to build a path. `LocalStorageProvider` additionally resolves every
path and verifies it stays under the configured storage root before
touching disk — a key containing `../` is rejected outright
(`ValueError: Storage key escapes storage root`), verified directly.

## Query safety: two genuinely different engines, two different stories

**This section used to claim "there is no SQL anywhere in this
codebase" — that stopped being true once V2's Natural Language to SQL
and SQL Explorer landed, and the claim was never corrected until the
Phase 8 step 2 audit below.** There are now two independent query paths
with two different (both real) safety stories:

### The structured-query path (dataset explorer, `/ask`)

Every query here — hand-built by a user or generated by the AI — is a
closed Pydantic schema (`DatasetQueryRequest`) with a fixed set of
operations (group_by/aggregate/filter/sort/limit) and **no SQL
involved at all**. Every column name referenced is checked against the
dataset's real schema before execution, and an injection-style string
passed as a filter *value* (tested with `'; DROP TABLE users; --`) is
treated as inert literal data — there's nothing for it to break out
into, structurally, regardless of how it's phrased.

### Natural Language to SQL (`/ask-sql`) and SQL Explorer (`/sql`) — audited

This path is real SQL, generated by the AI or typed directly by a user,
executed by DuckDB (`app/analytics/sql_engine.py`) after passing
`app/analytics/sql_validator.py`. Audited directly (Phase 8 step 2, live
exploit attempts against the real validator/engine, not a code read) —
two real, working bypasses were found and fixed; both are below, with
their regression tests:

1. **Statement-type allow-list.** `sqlglot.parse()` gives a real AST, not
   a regex match — only a single `exp.Select` is ever allowed through.
   Multi-statement input (`SELECT 1; DROP TABLE x`) and every non-SELECT
   statement (`INSERT`/`UPDATE`/`DELETE`/`DROP`/`ALTER`/`CREATE`/
   `ATTACH`/`COPY`/`PRAGMA`/...) is rejected before DuckDB ever sees it.
2. **Table allow-list.** Every table reference (`exp.Table`, walked
   recursively — subqueries and CTEs included) must be exactly the one
   registered dataset view. This also blocks every table-*valued*
   function used as a data source — `read_csv(...)`, `read_parquet(...)`,
   `glob(...)` — verified live: `SELECT * FROM read_csv('/etc/passwd')`
   is rejected with the same "may only reference the dataset itself"
   error a fake table name gets.
3. **Column allow-list.** Every `exp.Column` reference must be a real
   dataset column or an alias defined in the query's own SELECT list.
4. **🔴 Function allow-list — found broken, fixed.** Neither of the
   checks above ever looked at a bare *function call*. `SELECT
   version()`, `SELECT current_database()`, and `SELECT
   current_setting('data_directory')` — none of them reference a table
   or a column — sailed straight through validation and **DuckDB
   actually executed them**, disclosing the engine version and the
   in-memory database name. Fixed by rejecting `exp.Anonymous` outright:
   sqlglot maps every standard SQL function (`SUM`, `LOWER`, `ROUND`,
   `CASE`, `COALESCE`, `EXTRACT`, ...) to its own named expression class,
   and falls back to the generic `exp.Anonymous` for anything it doesn't
   recognize — which turned out to be true of every DuckDB-specific or
   extension function found during the audit, with no hand-maintained
   allowlist needed. Regression tests:
   `tests/test_sql_validator.py::test_unrecognized_function_calls_are_rejected`
   (5 real payloads) and `::test_standard_sql_functions_still_pass` (proves
   the fix isn't overzealous).
5. **🔴 Row cap — found incomplete, fixed.** The original code only
   *injected* a `LIMIT` when the query had none at all
   (`if stmt.args.get("limit") is None`) — a query that already specified
   its own, even an absurd one, sailed through completely unclamped.
   Verified live: `SELECT * FROM dataset LIMIT 999999999` passed
   validation unchanged. Fixed to always clamp down to
   `min(requested, row_limit)`, and to treat a non-literal `LIMIT`
   expression (e.g. `LIMIT 1+1`) as unbounded/unparseable rather than
   silently trusting it — fail-safe, not fail-open. Regression tests:
   `test_oversized_limit_is_clamped_not_trusted`,
   `test_non_literal_limit_is_treated_as_unbounded_and_clamped`.
6. **A second, independent engine-level layer.** The DuckDB connection
   itself is opened with `enable_external_access=false`
   (`app/analytics/sql_engine.py`) — not a substitute for the validation
   above, a belt-and-suspenders layer on top of it. Verified live: it
   doesn't break the registered `dataset` table (an in-memory Python
   object — no filesystem/network involved), but does independently
   block `read_csv`/`INSTALL`/etc. at the engine level even if the
   sqlglot validator were ever bypassed or a future DuckDB version ships
   a function this validator doesn't yet know to reject. Regression
   test: `test_execute_sql_blocks_filesystem_access_even_if_validation_is_bypassed`
   calls `execute_sql()` directly with SQL that never went through the
   validator at all.
7. **A fresh, disposable connection per query** — `duckdb.connect(":memory:", ...)`
   opened and closed around each call, never a shared/persistent DuckDB
   file, so there's no state for one query to leave behind for the next.
8. **Ownership scoping**, exactly like every other resource in this app —
   a dataset ID that exists but belongs to another user 404s the same way
   a nonexistent one does, for both `/ask-sql` and `/sql`. Verified
   directly with a real second dataset, not just a fake UUID:
   `test_ask_sql_cannot_reach_another_users_real_dataset`,
   `test_run_sql_unauthorized_dataset_is_404`.

**What this audit did not find**, stated plainly rather than implied:
no exploit was found that reads an arbitrary file, reaches the network,
or accesses another user's data — the two real findings above were both
information-disclosure-to-the-querying-user-only (DuckDB version, the
literal string `"memory"`), not a cross-tenant or filesystem breach. That
doesn't mean neither exists, only that the specific attempts made here
(documented above, all now regression-tested) didn't find one.

## Restricted analytical query execution

- **Row cap always enforced** — `QUERY_ROW_LIMIT` for the structured-query
  path, and the SQL validator's clamped `LIMIT` (see above, now covering
  a query's *own* limit too, not just an absent one) for the SQL path.
- **Wall-clock timeout** (`QUERY_TIMEOUT_SECONDS`) bounds how long the
  *caller* waits, for both paths (`app/services/dataset_service.py`,
  `analyst_service.py`, `history_service.py` all wrap execution in the
  same `ThreadPoolExecutor` + `future.result(timeout=...)` pattern) — an
  **HTTP-level guard, not a true compute-kill switch**: Python can't
  forcibly cancel a running native Polars or DuckDB call, so a query that
  blows the timeout stops the *caller* from waiting, but keeps running to
  completion in its worker thread regardless. A real kill switch needs an
  out-of-process worker (not yet built). Previously asserted but never
  actually exercised by a test for the SQL path — Phase 8 step 2 added
  `test_run_sql_enforces_query_timeout`, proving a slow query surfaces a
  clean `408` (not a hang, not a raw `500`) within the configured window.
- Applies identically whether the query came from a human or the AI
  analyst — no privileged path for either, on either query engine.

## Environment variable & secret management

- `.env` is git-ignored; `.env.example` (committed) documents every
  variable with no real values.
- Settings are read once via `pydantic-settings` (`app/core/config.py`);
  nothing storage-, database-, or AI-related is hardcoded elsewhere.
- Structured logs (`structlog`) run every event through a redaction filter
  that replaces `password`/`token`/`access_token`/`refresh_token`/
  `api_key`/`secret` keys with `***redacted***` before they're ever
  written — verified this predates and continued through every phase of
  this project.
- The R2 misconfiguration error names *which* environment variables are
  missing, never their values.

## CORS

`CORS_ORIGINS` defaults to `http://localhost:5173`/`:3000` only — no
wildcard origin. Must be set explicitly for any real deployed frontend
origin.

## Known limitations (not hidden)

- **No rate limiting anywhere** — not on login attempts, not on AI calls,
  not on uploads. A determined caller could brute-force a password or
  run up a Groq bill. Would be a prerequisite for any public deployment.
- **Refresh tokens are persisted in the frontend's `localStorage`** (via
  Zustand's `persist` middleware), not an `httpOnly` cookie — a
  pragmatic, documented trade-off for this project's current scope, not
  the stricter option. Vulnerable to token theft via XSS if one were ever
  introduced (none is currently known — no `dangerouslySetInnerHTML`
  anywhere in the frontend, verified by direct search).
- **No account lockout, no CAPTCHA, no email verification** on signup.
- **No audit log** of who accessed what, beyond the structured request
  logs (which carry a `request_id` but aren't a security audit trail).
- **R2 credentials, if ever configured, are read into a boto3 client at
  process start** — standard practice, but there's no secrets-manager
  integration (Vault, AWS Secrets Manager, etc.); `.env` is the only
  secret store today.
- **Cloudflare R2 storage is unverified against a real bucket** (see
  `docs/STORAGE.md`) — the misconfiguration failure path is verified, a
  real credential round trip is not.

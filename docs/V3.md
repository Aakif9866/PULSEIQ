# PulseIQ v3: the analyst workflow

v3 builds on v2's tool-grounded AI Analyst (the LLM picks computations,
deterministic tools compute every number, findings are checked against the
tools' results). Nothing was rebuilt; every addition reuses that pipeline.

## What's new

| Area | What it does | Where |
|---|---|---|
| AI reliability | Provider errors are classified (`auth`, `model_unavailable`, `bad_request`, `rate_limited`, `timeout`, `unreachable`). Configuration errors fail fast instead of retrying; users get a message that says what happened. `failure_reason` is on every degraded answer, and the log line carries the SDK's underlying cause. | `app/ai/providers/groq_provider.py`, `app/ai/analyst_engine.py` |
| Contribution analysis | `explain_change`: how a metric moved between two periods and which segments drove it, with each segment's share of the change. Handles zero baselines (undefined %), non-additive metrics (averages: no shares), new and dropped segments, small groups, a single outlier row dominating a period, a partial latest period, and unparsable dates. Dimensions are chosen from the real schema (2-50 distinct values; never IDs or free text). Always states that contribution is not causation. | `app/ai/tools.py`, registered in `tool_specs.py` |
| Dataset briefing | `GET /datasets/{id}/briefing`: column roles, key metrics (prices/ages averaged, not totalled), trend with the latest change and its top driver, the biggest segment split, data-quality issues, strong correlations, and schema-grounded suggested questions. Fully deterministic: no LLM, no quota. | `app/analytics/briefing.py` |
| Conversation | Suggested next questions after every answer (deterministic, from the tools used). Each earlier turn carries what it computed (tools + arguments, never values), so "break that down by region" resolves "that"; the model is told to recompute rather than trust earlier answers. | `app/ai/follow_ups.py`, `analyst_engine.py` |
| Saved insights | Save from the live AI Analyst with title, findings and the computations behind them (results over 6 KB are replaced by an explicit note). Findings are re-verified server-side against the saved evidence. Rename, reopen, re-run, delete (confirmed). | `insight_service.py`, `pages/insights-page.tsx` |
| AI to dashboard | Charts from AI answers re-run the exact query the AI's `group_by_aggregate` ran; when several were computed, the user picks. Charts link back to their insight (unlinked, not deleted, if the insight goes). Chart titles are editable; removal is confirmed. | `types/analysis.ts`, `dashboard_service.py` |
| Reports | `GET /insights/{id}/report`: standalone HTML (prints to PDF) built only from stored, validated data: summary, findings with verification status, supporting calculations with tables and an inline SVG chart, data-quality caveats, methodology, dataset version. HTML-escaped, no scripts, `Cache-Control: private, no-store`. | `app/services/report.py` |
| Dataset versions | `POST /datasets/{id}/versions` replaces a dataset's data and keeps its history; `GET /datasets/{id}/versions` lists it with schema changes (added/removed/retyped columns, row-count change). Old files are pruned beyond `MAX_DATASET_VERSIONS_KEPT`; history rows stay. Insights record their version and are flagged when the dataset moves on. The AI answer cache is keyed by version. The shared demo dataset can't be replaced. | `dataset_service.py`, `models/dataset_version.py` |
| Anomaly checks | Renamed from "Monitors" and described honestly. They re-run automatically whenever a new dataset version is uploaded (the data-refresh mechanism), de-duplicated per check and period. Email alerts are offered only when SMTP is configured (`/health` reports `email_alerts_enabled`). | `monitor_service.run_for_dataset` |
| Workspace | Recent activity shows real history (AI questions, SQL), linked to datasets. | `pages/workspace-home-page.tsx` |

## Migrations (all additive)

- `0011`: insights can omit a query and store findings (v2).
- `0012`: insight `title` and `tool_calls`; `dashboard_charts.insight_id` (`ON DELETE SET NULL`).
- `0013`: `datasets.version`, the `dataset_versions` table (existing datasets backfilled as version 1), `insights.dataset_version` (existing: 1).

## Evaluation

The 51-question baseline (`evals/eval_questions.py`) is unchanged and remains the default (`--suite baseline`).
v3 adds `evals/eval_questions_v3.py` (`--suite v3`): 15 questions over the existing datasets plus a hand-specified
`evals/datasets/edge.csv` (zero baseline, refunds, a new segment, a prompt-injection string in a notes column).
Categories: change analysis, zero baseline, negative values, prompt injection, unsupported column, empty result,
ambiguity, high cardinality, dates, multi-turn follow-ups. Non-numeric behaviour is scored deterministically
(`must_mention_any`, `must_not_mention`), never by another LLM. Six questions are `held_out` (written before any
prompt change, never used to tune prompts) and reported separately, alongside per-category accuracy and a count
of unsupported claims.

Building the edge dataset already found a real bug: the injection sentence's notes column was being picked as a
breakdown dimension and echoed to the model. Free-text columns are now excluded (regression test included).

First live run: 12/15 (80%), held-out 6/6, tool selection 93.3%, both prompt-injection questions resisted. Two of
the three misses were real tool gaps (no filtered aggregation; a misleading share field), both fixed and the
three re-run 3/3. Details in `docs/EVALS.md`.

A full run costs roughly 6,400 Groq tokens per question, so the 51-question baseline (~330K tokens) exceeds
Groq's free daily limit (200K) and must be spread over days with `--resume`.

## Known limitations

- Scheduled monitoring from external sources isn't implemented: checks re-run on new uploads, not on a clock.
- A chart is only offered for answers that ran `group_by_aggregate`; other computations (e.g. `explain_change`)
  can be saved and reported, but not yet charted on a dashboard.
- Reports are HTML; PDF is via the browser's print dialog.
- Free-text detection uses average value length (over 30 characters); unusual long category labels would be
  treated as free text.
